MemberJunction and Entity Framework Core 11

Two good ORMs built on opposite philosophies.

Entity Framework Core is the most widely used ORM in .NET. Its eleventh major version ships with .NET 11 on November 10, 2026. MemberJunction's ORM layer (BaseEntity, RunView, RunQuery and BaseEngine) solves the same problem from the other direction. This page compares the two fairly: where each one is better, where MJ has gaps and what is planned for them, and an honest assessment of performance.

01At a glance

The two aren't the same kind of thing, and that's the first thing to understand. EF Core is a data-access library: it maps C# classes to tables, translates LINQ to SQL and tracks changes. You build everything above it (API, authorization, caching, client) yourself. MJ's ORM is the foundation of a full-stack platform: the same entity object runs in the browser and on the server, and the API, security, audit and caching are generated or built in. A fair comparison has to keep both of those facts in view.

02Where the truth lives

In EF Core, the model is C# code. You write classes, configure them with attributes or the fluent API, and EF builds an in-memory model when the app starts. That model can be precompiled for faster startup. Migrations are generated by diffing the model against a snapshot. EF 11 makes that loop shorter: dotnet ef database update --add creates and applies a migration in one step, and the model snapshot now records the latest migration ID, so two branches with diverging migrations produce a merge conflict instead of a silent mismatch.

In MemberJunction, the database is the starting point. You write SQL migrations; CodeGen reads the schema and writes it as metadata rows (Entities, Entity Fields, Entity Relationships). From that metadata it generates the typed TypeScript entity classes, Zod schemas, base views, CRUD stored procedures, the GraphQL API and the forms.

This is the decision that explains most of the other differences. A model stored as data can be read by an AI agent at runtime. A model compiled into code can't.

The trade-off is real in both directions. Code-first gives C# developers refactoring tools, compile-time checking of the model and a model that changes together with the code. Schema-first fits organizations whose database outlives any one application (common for associations and nonprofits) and lets MJ work against databases it didn't create. It also lets MJ's agents and its semantic layer (the Canon) treat the data model as something they can read and reason about.

03The object model

EF: plain objects plus a context

Entities are plain C# objects that know nothing about the database. A DbContext does the work: its change tracker snapshots each loaded entity, its identity map guarantees one instance per row per context, and SaveChanges() computes the difference and writes it as a single unit of work. Context lifetime is the main design decision: usually one per request, pooled.

MJ: objects that carry their own state

Each BaseEntity holds its own fields, old values, dirty state, validation and lifecycle events, and you call Load(), Save() and Delete() on the object. There's no context to manage. Rows are hydrated lazily: a record loaded from a cache is near-instant until you touch a field that needs the full machinery. BaseEngine caches act as a long-lived, process-wide set of instances for reference data.

EF's model is cleaner for large write batches where everything should succeed or fail together. MJ's is simpler to use in UI code and agent code, where one record is loaded, edited and saved, and it's the reason the same object can work over the network (§10). Behavior also lives in different places. EF keeps rules in services, which is the usual "domain model" style. MJ puts them on the entity: generated value-list checks, Validate(), ValidateAsync() for checks that span records, and server-side subclasses registered with @RegisterClass. EF Core doesn't validate data annotations on save; MJ validates every save.

04Querying

LINQ is EF's strongest feature. C# expression trees let EF translate ordinary, type-checked C# into SQL, and EF 11 continues to improve that translation: a new FullJoin operator, MaxBy/MinBy, better GroupBy translation, redundant joins removed from split queries (one reported scenario got 29% faster), and no-op CASTs stripped so indexes stay usable.

MJ chose not to build a LINQ equivalent. TypeScript has no expression trees, and imitating LINQ with a query builder would give up the property MJ cares about most: queries that can be stored as data, reviewed, versioned and written by agents. MJ has three query surfaces instead:

  • RunView runs against an entity's generated base view, with a structured, typed Filter built via FilterOf<T>() (compiled to parameterized SQL and also evaluated in memory against BaseEngine caches), ExtraFilter, OrderBy, field projection, keyset paging, aggregates and a choice of result shape (plain rows for speed, full entity objects for editing).
  • RunQuery runs stored queries written in MJ Query Language: SQL in one dialect plus an allow-listed set of template tags for parameters, conditions, loops and composition. Each query is parsed and checked when it is saved. Parameter types are inferred, every value must go through an escaping filter, and {{query:"Path/Name(Arg=…)"}} includes another approved query as a CTE, with arguments passed explicitly like a function call. Queries carry doc comments, and branch variants are analyzed so that every possible output column is known.
  • Approved queries become ground truth — with generated typed wrappers. Queries users approve join the Canon, and CodeGen emits typed Queries.<Category>.<Name>.Run(params) wrappers with parameter and row interfaces, JSDoc comments, and SHA-256 signature drift checks (§13).

05Writes, transactions & entity graphs

EF generates parameterized INSERT/UPDATE/DELETE statements that include only the modified columns, batches them into few round trips, and wraps each SaveChanges() in a transaction. For set-based work, ExecuteUpdate/ExecuteDelete skip the change tracker entirely.

MJ writes through generated stored procedures (spCreate*, spUpdate*, spDelete*). A DBA can replace any of them, and each returns the saved row through the base view, so calculated and joined fields come back immediately. Every write can be recorded in Record Changes, MJ's built-in version history. There are three mechanisms for doing several things at once, each with a defined job:

EF has the advantage for bulk write throughput. MJ's per-record procedure, re-read and audit row cost more per write, but they produce the audit trail, refreshed calculated fields and cache invalidation that an EF application would have to build itself.

06Concurrency

Both handle concurrent edits, with different defaults and at different levels of detail. In the scenarios below, user A loads a record, user B then changes some of it, and A saves.

ScenarioEF defaultEF + rowversion tokenMJ over the wire
B changed Email; A saves TitleBoth kept (only modified columns are written)Rejected A's save fails, though the edits don't overlapBoth kept. The server merges from the stored row
Both changed Title to different valuesLost update last writer wins silentlyRejected with DbUpdateConcurrencyExceptionRejected with CONCURRENT_MODIFICATION_CONFLICT, naming the fields
Both set Title to the same valueFineRejectedAccepted (identical writes converge)
SetupNoneA token column per entityNone; on by default

How MJ does it: the client sends only the changed fields plus their OldValues___. The server loads the stored row and compares each changed field's old value, new value and current database value. It rejects a save only when a field the client changed was also changed in the database to something different. The comparison handles JSON key order and date precision.

Field-level conflict detection, on by default, is stronger than what EF gives you out of the box.

Server-direct saves get the same protection: the conflict detector and delta-only update binding live inside GenericDatabaseProvider. Whether a save arrives over GraphQL or runs directly on the server in an agent, action or scheduled job, the provider reads the dirty columns under an update lock (UPDLOCK, ROWLOCK on SQL Server, FOR UPDATE on PostgreSQL) inside the save transaction, checks for overlapping field edits against the caller's baseline, and sends only the dirty columns to generated spUpdate* procedures (§13).

07Inheritance

EF offers three strategies: table-per-hierarchy (the default: one table and a discriminator column), table-per-type and table-per-concrete-type. EF 11 extends complex types and JSON columns to TPT and TPC.

MJ's IS-A is table-per-type with a shared primary key, plus several things EF doesn't do. One object spans the whole chain: you set webinar.Name, webinar.StartTime and webinar.RecordingURL on a single instance, and Save() writes Product, Meeting and Webinar in one transaction. Subtypes can be overlapping, so one Person can be both a Member and a Speaker, which EF can't express because each row maps to exactly one CLR type. MJ also enforces disjoint subtypes when you want them, resolves the subtype when a record loads and protects parent rows from deletion while subtypes exist.

08Security

EF

Global query filters (soft-delete, multi-tenancy). Everything else, including who may read which rows and fields and who may update what, is application code in services and controllers.

MJ

Entity permissions, row-level security and field-level security, enforced in the ORM itself, with every entity operation running as the user who invoked it. A field the user can't read is never even loaded into the object. Values a client sends for fields it could never read are rejected. Agents act on behalf of a user and inherit that user's scope.

For a business application this is the largest difference in day-to-day work. With EF, authorization is something you design and build. With MJ, it comes from metadata.

09Caching

EF Core has no built-in data cache. It caches query translations and offers compiled queries and compiled models, but every query still goes to the database. The usual add-on is the third-party EFCoreSecondLevelCacheInterceptor, which invalidates by table when it sees a write. Its documentation notes that bulk ExecuteUpdate/ExecuteDelete bypass the interceptors, so they don't invalidate. Client-side caching is a separate layer you build.

MJ's cache is part of the ORM and is kept current by events:

There is a caveat. The server can trust its cache completely only because writes go through BaseEntity. Writes from outside MJ (another application, hand-run SQL) need MJ's external change detection to invalidate the cache. EF's approach of querying the database every time has no such dependency.

10One object model across the wire

An EF entity lives inside the .NET process that holds the database connection. To use the data in a browser you write an API, DTOs and a client model, then keep the three in sync.

An MJ entity is the same class everywhere. In the browser, BaseEntity talks to the server through GraphQLDataProvider; on the server, it talks to the database through the SQL Server or PostgreSQL provider. Validation, dirty tracking, related-record collections, IS-A chains and events behave the same in both places, and a composite save from the browser travels as one call. EF has no equivalent of this, because it was never designed to run on the client.

11AI & search: converging from different sides

EF 11 adds SQL Server 2025 vector search to LINQ: VectorSearch() with DiskANN vector indexes created through migrations (experimental in SQL Server, so the APIs may change), vector columns left out of SELECTs unless asked for, full-text catalogs and indexes in the model, and hybrid search that combines full-text and vector results with reciprocal rank fusion through FullJoin.

MJ has had entity embeddings, vector search and reciprocal rank fusion for a while. The difference is what sits above them: agents, prompts, the Canon of approved queries and documentation, and model-agnostic orchestration. EF ends at the data-access layer. MJ continues up to an AI layer that reads the same metadata the ORM runs on.

12Performance: a hypothesis, not yet a benchmark

We think MJ delivers better full-stack performance for the applications it's built for, because of its caching. We haven't measured it yet, so the scorecard below is reasoning, labeled as such. A reproducible benchmark is planned (§13), and its results will replace this section.

WorkloadExpected edgeWhy
Repeated reads of reference dataMJ, by a lotServed from cache with zero database queries on the server, and often with no round trip in the browser. EF goes to the database every time unless you add a cache.
Revisiting list viewsMJA fingerprint check confirms the cache is fresh without resending rows, and changes arrive as differences.
Many servers, many browsers, mostly readsMJRedis pub/sub keeps every server and connected browser current. In an EF stack that's infrastructure you build.
First read of a large resultEF.NET's no-tracking materialization is very fast. MJ adds a Node process, GraphQL JSON and object hydration (narrowed by plain-row results and lazy hydration).
Single-record save latencyEFEF runs one UPDATE of the changed columns. MJ adds a conflict read, a stored procedure that returns the full row, an audit row and cache invalidation. That's more work, but every part of it does something useful.
Bulk writesEF, by a lotStatement batching and set-based ExecuteUpdate/ExecuteDelete, compared with MJ's per-record procedure calls (transaction groups reduce round trips but not the work per record).
Cold startDependsEF can ship a precompiled model. MJ loads metadata and warms its engines, which costs time at startup and saves it on every request after.

The typical association application reads data far more often than it writes it. MJ should win there on user-perceived latency and database load, mostly by skipping work entirely. On bulk loads, ETL-style jobs and cold scans of large results, EF should win.

A fair benchmark compares like with like: MJ against ASP.NET Core with EF Core 11, a hand-built API and a typical client cache. It should run on the same database and schema, with an EF setup that a .NET specialist has reviewed and tuned (pooled contexts, compiled queries, no-tracking reads, with and without a second-level cache).

13Where EF is ahead, and what MJ shipped to close the gap

EF is ahead in maturity, provider breadth, bulk writes and compile-time-checked LINQ queries. MJ deliberately skips LINQ so queries remain data, and closed the three gaps surfaced by this comparison (plans/orm-improvements-ef-comparison.md):

1 · Concurrency checks for every save (Shipped)

Moved the field-level conflict check from the API layer into GenericDatabaseProvider, so server-side saves by agents, actions and jobs get it too. Every update sends only changed columns. The current row is read under an update lock inside the save's transaction, closing the race window, with configurable 'off' | 'log' | 'enforce' rollout modes.

2 · Structured filters in RunView (Shipped)

RunViewParams.Filter and BaseEnginePropertyConfig.Filter accept CompositeFilter JSON, compiled to parameterized SQL by CompositeFilterSQLCompiler and type-checked through FilterOf<T>(). The same filter runs against engine caches via BaseEngine.Where() and keeps cached datasets current when records change.

3 · Typed query wrappers (Shipped)

CodeGen emits typed parameter and row interfaces (Queries.<Category>.<Name>.Run()) for approved, reusable queries, using the types the MJ Query Language parser infers plus per-branch column presence (QueryField.InAllBranchVariants). Wrappers call RunQuery in the browser and on the server, with SHA-256 signature drift detection.

14Choosing

Choose EF Core when…

  • Your team and stack are .NET.
  • You want compile-time-checked queries and code-first modeling.
  • The workload is write-heavy, bulk or ETL-like.
  • You need a provider MJ doesn't support (SQLite, Cosmos DB, MySQL, Oracle) for reads and writes.
  • You're building the API, authorization and client layers yourself anyway.

Choose MemberJunction when…

  • You want one object model from the browser to the database.
  • Security, audit and caching should come from metadata rather than be built per app.
  • The database outlives the application, or you're working against one you didn't design.
  • AI agents need to read, query and reason over the data model at runtime.
  • The workload is a business application that reads far more than it writes.

They also work together: a .NET service can use EF for a write-heavy pipeline against tables that MJ also manages, reads and secures for everyone else. In that case, use MJ's external change detection so its caches see the writes EF makes.
