Two install defects found by a citizen agent builder tester.

**CodeGen's artifact check finds `mj_generatedentities` where MJAPI does.** The check used to look in fixed places: the install root's `node_modules` only before 6.2.0-edge.2, then that plus `apps/MJAPI/node_modules`. pnpm, the installer default, links the package into the `node_modules` of each workspace package that declares it, and that link exists from the moment `pnpm install` finishes. It never creates a root entry. So a correct first CodeGen attempt failed the check on a pnpm distribution install before 6.2.0-edge.2, and still fails it on a pnpm monorepo install, where MJAPI is `packages/MJAPI`. The check now follows Node's own resolution from wherever MJAPI lives: its own `node_modules`, then each parent's, up to the install root. When MJAPI cannot resolve the package, the phase fails at once and says to run `pnpm install`. It no longer rebuilds and retries, because only an install creates that link.

**The rebuild before a CodeGen retry is narrower.** A distribution install now rebuilds only `mj_generatedentities` and `mj_generatedactions` before retrying. Its CLI and every `@memberjunction/*` package come pre-built from npm, so those two are the only things that can be stale. It used to build the whole workspace, Explorer's production build included, which ran out of memory in an 8 GB container. A monorepo install keeps the full build, because there the CLI that runs CodeGen is built from the workspace.

**One copy of MemberJunction after an Open App install.** BizApps packages declare `@memberjunction/*` with ranges built against 6.1 (`~6.1.5`, `^6.1.0-edge.5`). Some of them are `dependencies`, and some are peers the host does not provide. Under semver neither kind of range matches a `6.2.0-edge.N` host, so `mj app install` of More Cheese put a parallel 6.1.5 tree into a 6.2.0-edge.3 distribution: 53 `@memberjunction` packages at two versions, `core` and `global` among them. That splits MJ's class registry, and entities and resolvers stop registering without an error. After its `pnpm install`, `mj install` now pins every `@memberjunction/*` package of the host's release to the host version, in the same `overrides:` block of `pnpm-workspace.yaml` as the Angular pins. pnpm has no glob override keys, so the names come from two places: `pnpm-lock.yaml`, and a list of the release's packages the installer ships (`dist/memberjunction-packages.json`, written at build time). The list covers packages only an Open App uses, such as `ng-gantt` and `ng-kanban`. They are absent from a fresh distribution's lockfile, so before this they came in at whatever version the app's own range allowed. A list from another major release is ignored. Each value is `'$@memberjunction/cli'`, a reference to the root manifest's exact CLI version, so `mj bump -r` moves every pin with it. The lockfile is then re-resolved so it records the overrides. Pinning is skipped, with the reason logged, when the root CLI is not an exact version or `apps/MJAPI` declares a different `@memberjunction/core`.

**`mj app install` / `mj app upgrade` warn when MJ is installed twice.** After the package install, the Open App engine reads `pnpm-lock.yaml` and warns when any `@memberjunction/*` package is installed at more than one version. The warning names the packages and versions and the host's MJ version, and says how to pin them. New export: `FindDuplicateMemberJunctionPackages()`.
