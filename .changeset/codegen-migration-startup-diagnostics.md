Four failure paths that reported the wrong cause or no cause at all in a multi-app workspace (#3975). Diagnostics only — no public signature is removed or changed, and each fix leaves the pass/fail outcome it reports alone.

- **CodeGen permissions no longer fail a run on another app's not-yet-generated object.** STEP 2(c) deliberately generates permissions files for the entities `excludeSchemas` removed, and STEP 4 executed them — so in a multi-app database, whichever app ran CodeGen first failed on a sibling app's missing `spCreate*`/`spUpdate*`, unavoidably, since the behaviour acts on precisely the excluded set. A missing target object on an out-of-scope entity is now skipped with a note grouped by schema; any other error still fails the run, and in-scope entities are unchanged.
- **A failed GRANT is reported as a consequence, naming the cause.** New `SQLExecutionDiagnostics` records each failed SQL batch as it happens (with the `CREATE`/`ALTER` target it was building, and the error in full rather than truncated to 200 chars), so `applyPermissions` can attribute `Cannot find the object 'X'` back to the creation failure that produced it, and the run's summary leads with the FIRST failure instead of a batch index.
- **App migration failures carry the migration file and the first database error.** `RunAppMigrations` now registers Skyway's `OnProgress` callbacks, because a failed batch's rich error is destroyed by the rollback it triggers: the rollback throws `Transaction has been aborted.` on an already-doomed transaction, that throw escapes, and `Migrate()` returns `Details: []` with only the abort message. `OnMigrationEnd` fires before the rollback. `FirstDatabaseError` additionally walks back through `mssql`'s `precedingErrors`, since the driver rejects with the LAST error of a chain — turning `Could not create constraint or index. See previous errors.` into the `Msg 1767` that names the actual invalid table.
- **An unloadable `dynamicPackages` entry is legible.** Under `ts-node/esm` a dynamic-import failure crossing the module-hooks thread arrives as a null-prototype object with zero own properties — `instanceof Error` false, no message, and `String()` on it THROWS — so MJAPI refused to start with no output whatsoever. New `describeThrown` renders such a value without coercing it, `describeHostResolution` pre-computes why the package is unreachable using a CJS resolver that never touches the loader hooks (so the explanation survives a failure the loader makes uncatchable), and the loader names the entry, its `AppName` and its `StartupExport`, reports every host anchor tried, and warns loudly at the end of the phase for each app whose resolvers and class registrations are missing from the running API.
