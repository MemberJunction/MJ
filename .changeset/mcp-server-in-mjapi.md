The MCP server can now run inside MJAPI. Stock MJAPI depends on the package but does not load it; list `@memberjunction/ai-mcp-server` in `dynamicPackages.server[]` (with `Processes: ['mjapi']`) and MJAPI mounts the new `MCPServerExtension` at `/mcp` under `MJAPI_BASE_PATH` (so `/api/mcp` when MJExplorer owns `/`). It uses MJAPI's database connection, builds its OAuth resource URL from `MJAPI_PUBLIC_URL`, and keeps every MCP route, OAuth discovery document and OAuth proxy route under the mount. The standalone server is unchanged and still supported.

- MJAPI no longer gzips `text/event-stream` responses, which held back streamed MCP replies until they finished.
- The OAuth proxy parses request bodies only under `/oauth`, so with the proxy enabled it no longer swallows legacy SSE `/mcp/messages` bodies.
- Inside MJAPI, the extension refuses to mount with `mcpServerSettings.auth.mode: 'none'`, with `systemApiKey` still the published placeholder `MY_API_KEY_FOR_MCP_SERVER`, with MJAPI multi-tenancy on, or while any server middleware other than Diagnostics adds after-login handlers (they never run for MCP requests). MJServer exposes `GetActiveServerMiddleware()` for this. It accepts API keys only in headers, and warns when `auth.resourceIdentifier` overrides the served URL and when `trustProxy` (which has no effect there) is set. It also serves the OAuth discovery documents at the path-insertion URLs the MCP SDK requests (`/.well-known/<doc>/mcp`), and follows MJAPI's `cors.allowedOrigins`.
- MCP API keys now carry their row-filter bindings and acting context, as they do on MJAPI's GraphQL: a key restricted to certain rows was unrestricted through MCP. The system key is compared in constant time, and the boot log no longer prints part of `MJ_API_KEY`. The system key's refusal on scope-checked tools is now explicit, with a reason.
- MCP refuses MJAPI's magic-link and realtime-widget guest tokens, which verified against MJAPI's registered issuer and would have given a guest the full rights of the user its email maps to.
- Sessions, on both transports: every request is authenticated, including each legacy SSE message post, and must come from the exact credential that opened the session (a revoked key stops working at once, and another key of the same user cannot borrow the session). An unknown Streamable session gets the spec's 404, sessions are registered before the initialize response goes out, no session server is built for a request that is not an initialize, and idle sessions close after 30 minutes instead of leaking. CORS allows `DELETE` and the MCP headers. A 401 no longer advertises `resource_metadata` while OAuth is off, including when the default `both` mode falls back to API keys because no OAuth provider is configured.
- The OAuth consent form posts to the proxy's base URL instead of a hardcoded `/oauth/consent`. With the OAuth proxy and MJExplorer at the host root, one web-server rewrite is needed for login-server discovery; the package README gives it.
