Integration Test TestType — graduation Phase 5: standing CI/release gate, dashboard legibility, and multi-platform/cross-server seams.

- **Deterministic integration tier is now a runnable CI gate.** New `run-all.ts` aggregator + root `npm run test:integration` script: spawns each deterministic, server-side suite (`server-cache`, `runquery-cache`, `dataset-cache`, `aggregates-cache`, `rls-isolation`) in its own process so each owns `LocalCacheManager.Initialize` as first caller (D1), and collapses the per-suite `0/1/2` exit codes into one. Excludes `client-cache-tests.ts` (needs a running MJAPI) and `cross-server-invalidation-tests.ts` (opt-in behind `RUN_CROSS_SERVER=1`). Verified locally end-to-end: 5/5 suites pass, overall exit 0.
- **CI workflows.** The deterministic SQL Server tier is defined ONCE in a reusable `integration-run.yml` (`workflow_call`: Docker `db-setup` provisioning + the in-process `npm run test:integration` aggregator) and shared by two callers, so PR and release runs are byte-for-byte identical: `release-test.yml` runs `unit-tests` then calls it as `integration-suite`, and `integration.yml` calls it as the blocking PR gate. The heavy full-stack browser regression job was removed (much too heavy for this tier). No PostgreSQL CI lane (see the seam note below).
- **Dashboard legibility (D5.4 / D10).** Reconciled the custom `MJ: Test Runs` form: `getCheckResults()` now reads `ResultDetails` as the **bare `OracleResult[]` array the engine actually writes** (mapping `oracleType` → display name) instead of the never-written `details.checkResults` object — un-breaking per-check rendering for ALL engine-produced runs. The mapping is extracted into an Angular-free `test-run-checks.ts` (unit-tested, 9 cases). Bound the `<mj-execution-context>` widget in the Testing dashboard runs view to the run's machine/CI fields (threaded `MachineName`/`MachineID`/`RunByUserName`/`RunByUserEmail`/`RunContextDetails` through the run summary + its RunView projection). Custom-form module wiring confirmed already correct.
- **PostgreSQL provider-selection seam (D5.5).** `DbConfig` gains a `Platform` field (`DB_PLATFORM` ∈ {sqlserver, postgresql}, default sqlserver); `bootstrapIntegrationServer` dispatches to the SQL Server path (unchanged, proven) or a PostgreSQL path that does the real `PostgreSQLDataProvider` Config + `SetProvider` (dynamically imported — optional dependency). The bootstrap context's `Pool` is now optional with a platform-agnostic `ClosePool()` (mssql `pool.close()` / pg `pool.end()`); the five standalone scripts call `ic.ClosePool()`. The PG path surfaces the missing PG-aware user-cache bootstrap (a tracked Phase-0 prerequisite — `UserCache.Refresh` is mssql-only) as a clear error rather than fabricating a user. The seam ships, but there is **no PostgreSQL CI lane** yet — a runnable one needs both that user-cache gap closed and a PG migration path, so it's deferred rather than carried as a non-functional job. Platform-selection logic is unit-tested.
- **Cross-server Redis invalidation spec (D5.6).** New `cross-server-invalidation-tests.ts` (gated `RUN_CROSS_SERVER=1`) connects two GraphQL clients to two MJAPI processes sharing one DB + one Redis, and proves a `Save()` in process A invalidates the cached read in process B (the transport — `RedisLocalStorageProvider` pub/sub → `LocalCacheManager.DispatchCacheChange` → remote-invalidate — already ships; this exercises it). Plus a `docker-compose.cross-server.yml` overlay (shared Redis + a second `mjapi-b` replica).
- All changes additive / back-compat. SQL Server path re-verified live after the `ClosePool` refactor; testing-integration unit tests 69 pass; core-entity-forms 24 pass; both Angular packages build clean.
