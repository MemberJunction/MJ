Stop the view settings panel from undoing the grid's refusal of a saved layout that belongs to a different entity (follow-up to MemberJunction/MJ#4656). Opened on such a layout, the panel loaded its aggregates verbatim — listing, say, "Open Orders" as configured while the grid showed no card — and hid every column, because none of the foreign names matched. Saving then wrote this entity's real columns next to those aggregates, and even when the panel held none, `view-workspace` read the missing config as "keep the existing aggregates" and restored them from the live grid state. Real columns plus foreign aggregates is a state the grid believes, so it computed them and the wrong numbers came back for good. The panel now applies the grid's own rule through a new shared `SavedColumnsMatchEntity()`: a saved column list naming none of the entity's fields came from elsewhere, so it shows the entity's default columns, does not load that layout's aggregates, and shows a notice explaining why and that saving replaces the old layout. When a layout had aggregates and the panel now holds none, it saves an explicit empty list instead of `null`, so nothing restores them — which also fixes removing the last aggregate of a view, a deletion that previously did not stick.
