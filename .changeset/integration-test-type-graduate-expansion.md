Integration Test TestType — graduate the `next` expansion suites into metadata bundles + unify the two RLS implementations.

Graduates the standalone `tsx` integration suites (previously runnable only via `tsx`/`run-all.ts`, invisible to `IntegrationTestDriver`/`mj test`/`TestRun`) into first-class metadata-driven check bundles. Each `next` script is now a thin dispatcher of a registry bundle, so `run-all.ts` and the driver share ONE definition (single source of truth).

- **RLS merge (Phase A).** Collapsed the two overlapping-but-non-identical RLS implementations (the package fingerprint/cache bundle + `next`'s inline `rls-isolation-tests.ts`, whose local ids collided) into ONE canonical `rls-isolation` bundle, renumbered RLS1–RLS7 with no collision. Now the superset: RLS1 `{{UserID}}` token substitution, RLS2 distinct self-scoped predicate text, RLS3 fingerprint divergence, RLS4 server-superset no-cross-serve, RLS5 live-RunView scoping, RLS6 always-runnable empty/non-empty fingerprint invariant, RLS7 client smart-cache (client transport). `RlsFixture` gained `TokenFilter` + `LivePair` (discovered, never minted), each guarding its own checks so partial fixtures degrade gracefully. IT06 now covers the whole superset; the duplicate inline script body is gone.
- **6 deterministic server bundles graduated (Phase B):** `record-process` (RP1–8), `record-process-facade` (RPF1–2), `scheduled-jobs` (SJ1–2), `field-rules-bulk-update` (FR1–3), `remote-operations` (RO1–7), `ai-skills` (21 checks) — check bodies lifted verbatim into `src/checks/*.checks.ts`, registered in the `IntegrationCheckRegistry`, with metadata `Test` records IT04/IT05/IT09/IT10/IT11/IT12 joined to the "Integration Tests — Deterministic" suite.
- **New bundle-lifecycle mechanism.** Generalized the driver's one-off runquery fixture hook into a per-bundle `BundleLifecycle` (`RegisterLifecycle`/`GetLifecycle`): Setup creates a shared fixture on the context, Teardown removes it in FK-safe order (best-effort, never masks a result). Both the driver and the dispatcher scripts wrap a bundle's checks in Setup→run→Teardown, so mutating suites self-clean identically on either path. `runquery-cache` migrated onto it. Per-bundle typed fixture fields added to `IntegrationCheckContext`; `settle` moved into the package.
- **Driver provider fix.** `buildCheckContext` (server transport) now threads the real `DatabaseProviderBase` (bootstrap's own provider, else `Metadata.Provider`) instead of `this.Provider`'s `new Metadata()` facade — the facade lacks `IRemoteOperationProvider.RouteOperation`, so the remote-operations + AI-Skills remote-op checks would spuriously fail under the driver. The driver path now faithfully mirrors the dispatcher path.
- **New direct deps** (already present transitively via `server-bootstrap-lite`): `@memberjunction/aiengine`, `ai-core-plus`, `ai-agents`, `actions`, `scheduling-engine`, `record-set-processor`, `record-set-processor-base` — the engines the graduated check bodies call.
- Verified live against SQL Server (`mj_integrations`): all 6 dispatchers pass (43/43 checks); the driver runs all six IT records green; `record-process` and `ai-skills` golden-diffs are script↔driver EQUIVALENT. Package unit tests: 98 pass (coverage-loss guard extended to every bundle). No `mj:manifest` change (no new `@RegisterClass` — bundles/lifecycles register at module load). Additive / back-compat.

Note: three checks from the `next` merge (server-cache S28/S31, aggregates AGG3) fail identically in BOTH the standalone script and the driver — they are pre-existing, in bundles this change does not touch, and are out of scope here (flagged for separate investigation; S31 is a cache cross-user-permission check that may reflect this DB's user set rather than a product regression).
