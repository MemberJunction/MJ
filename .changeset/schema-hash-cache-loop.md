Servers sharing a Redis cache no longer evict each other's cache entries in a loop when they disagree on an entity's field list, which is the normal state during a rolling deploy that ships a migration. A schema-hash mismatch on a shared store is now a local cache miss: the slot is no longer deleted (a delete is published to every server, whose engines reload and rewrite it). Each slot also records the newest metadata timestamp of its entity, so a server that finds a slot written under newer metadata stops writing that entity's slots until its own metadata changes. For any other mismatch, a server writes the entity's slots at most once a minute, which keeps a peer still running older code from turning each of its reads into a delete. Process-local stores and in-place slot maintenance still delete a mismatched slot. `BaseEngine` now coalesces reloads triggered by peer cache events: events for one property that arrive during a reload share a single follow-up reload. A peer's cache payload whose schema hash differs from the engine's own is no longer loaded into the engine (rows from a server on older metadata lack the new columns, which left them null on every row); the engine reloads instead. The `[CACHE-SCHEMA-STALE]` warning is logged once per entity and hash pair per process.
