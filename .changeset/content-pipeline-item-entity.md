Content pipeline: Content Items can be a product's IS-A extension of `MJ: Content Items`. The pipeline always created, loaded and saved items as `MJ: Content Items`, so an item it created had no extension row, stages could not read the extension's fields, a driver's `Columns` naming one was refused, and vectors could not carry one. A source's items are now the entity named by its `Configuration.ItemEntity`, else its Content Source Type's, else its Content Type's, else `ContentPipeline.ItemEntity` on the default AI Configuration (beside `ContentPipeline.DefaultVectorIndexID`), else plain `MJ: Content Items` (`ItemEntityResolver`). The hydrator reads items as that entity (using the extension row MJ's IS-A discovery already links when it loads the core row); the committer creates new items as it, so their save writes the extension row too, and gives an existing item that lacks one its row (`AttachToParent`) before committing to it; `Columns` are checked against the extension's fields, with the framework-owned columns still refused; Embed loads items as their entity, so `VectorMetadata` can name extension fields (a `FieldStrategy` of `all` or `exclude` now includes them). A name that is not an entity, or not an extension of `MJ: Content Items`, fails the item rather than creating it without its extension row. `ItemEntity` is added to the typed Configuration of Content Sources, Content Source Types and Content Types. No schema change.
