Three defects that broke or misdiagnosed a distribution install.

**Explorer loads one copy of Angular.** MJ's Angular packages declare Angular only as a peer range, so with nothing pinned at the workspace root pnpm 10 filled those peers with the newest Angular release while `apps/MJExplorer` pins an exact one. Two copies of `@angular/core` loaded and Explorer rendered a blank page (NG0203 on `MSAL_INSTANCE`). The installer now writes a top-level `overrides:` block into the workspace's `pnpm-workspace.yaml` that pins every `@angular/*` package, `rxjs` and `zone.js` to the versions `apps/MJExplorer/package.json` declares, read at install time so the pins move with Explorer. pnpm applies overrides to peer ranges too, which collapses the graph to one copy. An existing `overrides:` block is merged into (other entries and comments kept, stale Angular pins updated) rather than duplicated. A monorepo install, which has no `apps/MJExplorer`, is left as it was. The installer warns when it cannot apply the pins: when the existing `overrides` key is not a block mapping, or when the root `package.json` declares `pnpm.overrides` or `resolutions`, because pnpm then ignores the YAML block entirely.

**Injected environment variables reach MJAPI.** `distribution.turbo.json`, the repo-root template every install ships as `turbo.json` (not part of any package), gave the `start` task no environment passthrough. turbo 2's strict environment mode therefore stripped `AI_VENDOR_API_KEY__*`, `DB_*`, `MJ_BASE_ENCRYPTION_KEY`, auth and `REDIS_*` variables passed to the container before `turbo start` launched MJAPI. The persistent, uncached `start` task now sets `passThroughEnv: ["*"]`. `build` is unchanged: it stays in strict mode and its cache key does not move.

**A missing database is no longer blamed on the credentials.** SQL Server reports a missing database as `Login failed for user '…'` (error 18456), the same message as a wrong password, so `mj migrate`'s connection preflight told users to check `codeGenLogin` / `codeGenPassword`. On a SQL Server login failure the preflight now makes one short connection to `master` with the same login and runs a parameterized `SELECT DB_ID(@db)`. If that login works and the database is absent, the new `database-missing` reason says the database does not exist on that server and how to create it (`CREATE DATABASE`, or the `mj-db-setup.sql` script `mj install` generated). If the database exists, the message says the login cannot open it, instead of blaming the password. If the probe fails, the original message stands. The probe has a 5-second budget and always closes its connection.
