WS1: Update RLS now validates the post-image, not just the pre-image. WS2: multi-tenancy injection and session-isolation hardening.

**WS1 — `@memberjunction/core` / `@memberjunction/generic-database-provider`.** Saving an existing record only ever validated Update row-level security against the row as it currently exists in the database (the pre-image). A caller who legitimately owned a row could set a filter-referenced column (e.g. `OrganizationID`) to a value outside their own RLS filter and the save would succeed, because nothing re-checked the values actually being written. `DatabaseProviderBase.Save()` now runs a second, additive RLS gate (`CheckUpdateRLSPostImage`) after before-save hooks complete, using the same synthetic-row technique `CheckCreateRLS` already uses for new records — built by a newly generalized `BuildRLSProjections`, which also now emits every non-virtual field for the post-image check (typed `CAST(NULL AS <type>)` for nulled columns, not omitted) and validates numeric-field values before interpolating them (`CheckCreateRLS`'s non-quoted branch previously interpolated `String(value)` raw). A resolved filter that fully decomposes into simple `Column <op> <literal>` AND-terms with no dirty referenced column skips the extra check as a cost-control optimization; anything the parser can't fully prove decomposed — OR, function-wrapped columns, subqueries, no dialect wired — always runs it. The existing pre-image check and its "not found or access denied" message are unchanged; the post-image failure gets a distinct message. Create's existing pre-hook `CheckCreateRLS` call is also unchanged; a second, additive post-hook call now closes the analogous gap where a before-save hook could mutate a filter-referenced field after the first check passed.

Behavior note for deployments with an Update RLS filter: a save that reassigns a filter-referenced column away from a value the caller's filter permits will now be rejected, where it previously succeeded. This is the intended fix — not aware of any deployment that relies on the old behavior for a non-exempt principal, but if one legitimately needs to reassign such a column, prefer narrowing the Update filter to permit that transition over granting RLS exemption (exemption is broad and weakens the boundary elsewhere).

**WS2 — `@memberjunction/server`, multi-tenancy (opt-in, default off).** Two defects in `packages/MJServer/src/multiTenancy/index.ts`:

- The tenant-header predicate was built by direct string interpolation (`` `[${tenantColumn}] = '${tenantId}'` ``) with no validation and no escaping, and the tenant column was interpolated as a hardcoded, SQL-Server-only bracket identifier. `attachTenantContext` now validates every tenant id (regardless of source) against `^[A-Za-z0-9_.-]{1,128}$` and throws rather than degrading to an unscoped session; `createTenantMiddleware` responds 400 on a malformed or repeated header and never calls `next()` in that case. The predicate-building hook additionally escapes the tenant id at construction (defense in depth), verifies the tenant column resolves to a real, non-virtual field on the entity, and quotes it via the provider's own `QuoteIdentifier` instead of hardcoded brackets — fixing an existing PostgreSQL incompatibility as a side effect.
- `createTenantMiddleware` mutated `userPayload.userRecord` in place, which may be the shared `UserCache` instance for both JWT and API-key sessions — concurrent requests for the same user with different tenant headers could race on one object. A new shared helper (`cloneUserInfoForSession`, also now used by the existing magic-link session-scoping path) clones to a fresh `UserInfo` before stamping any per-request state.
