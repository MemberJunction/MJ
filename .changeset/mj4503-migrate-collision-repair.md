When a migration fails on a primary-key collision (SQL Server error 2627), `mj migrate` now adds — after the raw error — the table and GUID of the row already holding that key, and a ready-to-paste `mj migrate repair` command for it. Before offering that command it reads the failing migration, which is still on disk at that moment, and checks that the colliding GUID actually appears in it: if the row is not one that migration creates, no repair command is printed and the output says the row must be investigated manually; if the migration file cannot be read, the command is still offered but the output states plainly that the check did not run. The new `mj migrate repair` command deletes exactly that one row, after showing a preview of its identifying columns and confirming (`--yes` for non-interactive use); its optional `--migration <path>` re-applies the same scope check at delete time for anyone who still has the file. Together these let an operator clear a row that a database already holds ahead of the migration chain and re-run the upgrade, without hand-editing the database (#4503).
