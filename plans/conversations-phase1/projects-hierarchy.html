Sharing boundary — planned (last in build sequence)
The vision: share the project, not N individual things. Reality check (verified): person-to-person sharing is real today (Resource Permissions, View/Edit/Owner + a working Sharing Center), but the share modal's "anyone with the link" toggle is cosmetic — it writes nothing; the PublicLink token table exists and is never used. Project-boundary sharing would come from the generic ACL layer (AccessControlRule — dormant, no write UI) since the Project table has no owner or member fields of its own.
Reading the tree: everything project-related is optional. A chat can live in no project at all ("Ungrouped"), and today only Conversation.ProjectID is actually wired — so the honest current-state hierarchy is just Project → Conversations, with artifacts and workflows hanging off messages regardless of project. The rest of the picture is what P1.6 and "Projects v1" would attach.

Deliberately outside the hierarchy

🕘 Routines

Personal standing orders, run as you, no ProjectID anywhere. They appear in every mockup only as the global sidebar footer. Open question: should they join the tree?

🕶 Temporary chats

Never join a project, never read or write memory (D20 — chosen at creation, locked after).

🌐 Global memory

Notes with no project: inject everywhere. Project notes add to these, never replace them (D6, "broad" inheritance).

👥 People — an overlay, not a level

Ownership differs per level: conversations/artifacts/routines strictly one-user; collections optionally owned; projects ownerless. Agents are first-class actors (task assignees, memory holders). MJ today = single-player + grants; the mockups' "Members" imply multiplayer with zero schema backing.

The six open hierarchy questions

Each pin on the diagram marks where the question lives. None of the three Projects mockups answers them — they all render a single flat project.

1
Roll-up: what does a parent project's hub show — its own content only, or its descendants' conversations, memory, workflows, and artifacts too?
2
Memory inheritance: P1.6's rule is flat (project X or global). Should a chat in "Speakers" also hear what agents learned in "Membership Renewal"? Not covered by D17–D20 — worth raising while P1.6 is in flight.
3
Sharing cascade: if the project is the sharing boundary, does sharing a parent grant its children? Does project access reach every conversation and artifact inside? "Comprehensible in 5 seconds" is hard when the boundary is a tree.
4
Single-homed: a conversation belongs to exactly one project (plain FK, no tags, no many-to-many). A chat can't serve two initiatives. Fine for v1 — but it's a baked-in modeling commitment.
5
Two trees: Projects nest, Collections nest, and the proposal relates them. Users must intuit the difference between two nesting systems — a naming/affordance problem.
6
Move semantics: reparent a chat to another project — do its learned memories move, stay, or ask? (Audit half solved: D17 stamps runs with the project at run time, freezing provenance.)
