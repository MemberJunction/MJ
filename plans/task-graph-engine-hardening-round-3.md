## Executive Summary

A three-track adversarial review of the engine as merged — dispatcher core, graph algorithms, and the service/delivery/settlement layer, plus a pairwise audit of the Round 2 fixes against each other and the invariants list — reached two conclusions:

1. **Round 2 held at its anchors.** Every R2 fix was re-audited fresh and its stated mechanism is present and working: the reclamation predicates cover prompt tasks, the settle verdict gates the marker, the null-safe envelope ends the routine-absence holds, `terminalDecides` is semantics-aware in the exclusive dialect, `Cancel` reports honestly and follows nested graphs, the startup sweep drains. Nothing regressed.

2. **Six of the Round 2 fixes have residual gaps one layer out from their own anchors.** The pattern of this round is not new seams but *incomplete closures*: R2-10's ordering fix rests on a premise the claim loop falsifies (R3-1), R2-4 gated one dialect and left the other semantics-blind (R3-2), R2-3's absence classifier misses operator shapes its own validator blesses (R3-6), R2-5's determinism tiebreak is locale-dependent (R3-7), R2-2 shipped only half its own fix specification (R3-8), and R2-13's drain purge races the registration it purges (C5). The worst items share the signature failure mode of both prior rounds: **wrong work executes, or the record is silently rewritten, under a clean verdict.**

Every finding below was adversarially verified against source at `b7e4dae77` before this plan was written — most by two independent votes with matching anchors — and carries its verification status. Ordering follows the established doctrine: silent-wrong-outcome fixes first, each landing in the same commit as the test that fails without it.

**The three headline defects:**

- **R3-1** — `endGraphEarly`'s sibling skips are unguarded full-row saves against a stale snapshot: a sibling claimed mid-loop is overwritten to `Skipped` *while its body executes*, its outcome refused and discarded — the graph settles `Complete` with unrecorded work having run.
- **R3-2** — under `failureSemantics: 'block'` (the spec default), a `Failed` origin still decides its **ordinary** conditional edges; a false verdict converts the block cascade into a skip cascade, and work executes downstream of an unhandled failure — R2-4's exact catastrophe, reproduced through the dialect R2-4 did not gate.
- **R3-3** — the flow-dialect condition roots `data` and `context` resolve against the origin task's output instead of the invocation's runtime parameters; every documented `data.x`/`context.x` condition evaluates false on the dispatcher, silently taking branches the legacy walker never took. This is carried-forward **D2 made concrete** — it lands now, not as a design note.

## Phase A — Silent-wrong-outcome fixes

> One PR for the round is fine; keep fixes in separate commits, each with the regression test that fails without it.

### R3-1. `endGraphEarly`'s sibling skips must be guarded writes behind a durable early-finish declaration

**Severity: HIGH. Verified: CONFIRMED (two votes, both executed the trace against source). This is R2-10's fix incomplete — it refutes that fix's own stated premise.**

**Defect.** R2-10 moved the early-finish sibling skips after `CompleteClaimed`, justified by "the siblings are Pending and unclaimed until the skip lands" (Round 2 plan, R2-10 item 2). That premise is false. `endGraphEarly` loads a one-shot sibling snapshot (`loadChildTasks`, `packages/TaskGraph/src/TaskGraphDispatcher.ts:1227`), then writes each snapshot-`Pending` sibling `Skipped` via unconditional full-row `BaseEntity.Save()` (`:1229-1230`) — the exact write shape `TaskClaimStore`'s own header condemns (`TaskClaimStore.ts:41-46`). The early-finish decision exists only in the finishing instance's memory (`result.ChatMessage`): `loadGraphState`'s skip seeds derive solely from durable condition/exclusive-group state (`:2322-2337`), so **no claim filter anywhere can know about it** — R2-14 closed this identical window for cascade skips, but early-finish skips appear in no filter set. And because `executeClaimed` is not awaited (`:670`), even the *same instance's* next poll tick runs concurrently with the skip loop, with awaited `resolveOwner`/emit calls between saves widening the window.

**Failure scenario.** Prompt task T returns `ChatMessage='done'`; instance A records T `Complete` and enters `endGraphEarly`. Its own poll tick (or a peer's) fires mid-loop: sibling X is durably `Pending` with satisfied prerequisites (T's completion just landed; or an earlier sibling's `Skipped` satisfies), passes every filter, `TryClaim(X)` succeeds (`TaskClaimStore.ts:100-115` requires only `Status='Pending'`), and X's agent body starts. The loop reaches X: the stale snapshot says `Pending` (`:1228`), the full-row save overwrites `In Progress`→`Skipped` and `ClaimedBy`→NULL mid-execution. X's heartbeat fails; its `CompleteClaimed` is refused (`:147-195`); the agent's real side effects — billed tokens, sent emails — fired while the durable record says the step was never taken, and its `OutputPayload`/`AgentRunID` are discarded. `FindOrphanedInProgress` cannot see a `Skipped` row. The graph settles `Complete`. Nothing anywhere records that X ran.

**Fix specification.** Two coupled halves, mirroring the P1/R2-14 architecture:

- **Declare before mutating.** Persist the early-finish decision durably *before* the skip loop — a guarded `JSON_MODIFY` stamp on the parent's metadata bag (the continuation-CAS write discipline, `TaskClaimStore` owns it), and have `loadGraphState` fold declared-early-finish siblings into the claim filter's skip-seed set. That closes the window for every instance including this one.
- **Guard every skip write.** Replace the per-sibling `Save()` with a single-statement claim-store write: `UPDATE ... SET Status='Skipped' WHERE ID=@id AND Status='Pending' AND ClaimedBy IS NULL`, rowcount verdict. Rowcount 0 means a claim won the race: leave the row alone, let the executor's guarded completion land, and count it in the early-finish bookkeeping honestly (the graph can still settle; the sibling's outcome is preserved).

Audit the condition-cut skip path (`propagateAndRollup`'s cascade writes, `:823-846`) for the same shape — it carries a `Status==='Pending'` in-memory check today; it should carry it in the statement.

**Tests.** IT74 extension (**TX18**): trigger an early finish with a slow stub sibling; interleave a claim between the snapshot load and the skip write (test hook or a second dispatcher on the same DB); assert the claimed sibling is not overwritten, its `CompleteClaimed` lands, and the graph's final state records its outcome. Unit test on the guarded-skip statement's rowcount verdicts across all four pre-states (Pending-unclaimed / claimed / terminal / missing).

### R3-2. R2-4 completed: `failureSemantics` must gate the **ordinary** conditional dialect too

**Severity: HIGH (block is the spec default — every agent-emitted graph). Verified: CONFIRMED (one vote executed the scenario against the real built modules; differential control confirmed).**

**Defect.** `TERMINAL_FOR_CONDITIONS` unconditionally includes `Failed` and `Cancelled` (`packages/TaskGraph/src/condition-gate.ts:47-52`), and `DecideGate` (`:148-180`) has no `failureSemantics` input — R2-4 threaded semantics only into `ResolveExclusiveGroups`' `terminalDecides` (`TaskGraphDispatcher.ts:2265-2267`), leaving the ordinary dialect semantics-blind. Under `'block'`, whose own contract says "a failure is terminal for dependents" and reserves edge evaluation for `'edges'` (`task-graph-spec.ts:238-244`), a `Failed` origin's ordinary conditional edge that evaluates false is **dropped** (`:2279`) → target lands in `unreachableTaskIDs` (`:2304`) → seeds the skip cascade (`:2333-2337`) — and the dropped edge simultaneously severs `ComputeTasksToBlock`'s forward walk (`graph-algorithms.ts:237`, adjacency built from `liveEdges`), so nothing blocks. `Skipped` satisfies prerequisites; a join fed by an independent healthy route executes downstream of the unhandled failure. R2-3 made this far *more* reachable: a failed step almost never has output, so the null-safe envelope answers nearly every positive condition with a confident false→drop where it previously threw→held visibly. The parent still rolls up `Failed`, so the verdict looks right while the join's side effects have fired. The `Cancelled` variant is identical mechanics — after R2-9's partial-cancel fix deliberately leaves a graph active, a `Cancelled` child's false conditional edge skip-releases downstream work in a workflow the user cancelled.

**Failure scenario (executed against the built modules).** `A →(payload.approved === true)→ B → D`, plus `E → D`, semantics `'block'`. A fails with no output → condition false → drop → B `Skipped` (not `Blocked`) → `toBlock=[]` → D eligible, claimed, executed. Actual pipeline output: `unreachable=[B]`, `cascadeSkip=[B]`, `toBlock=[]`, `eligible=[D]`. The same graph with an unconditional A→B edge correctly blocks B and D.

**Fix specification.** Thread `failureSemantics` into the ordinary-edge decision, mirroring R2-4's exclusive fix: under `'block'`, a `Failed` origin's conditional edges are **not evaluated and not dropped** — `DecideGate` returns `keep`, the edge stays in `liveEdges`, and `ComputeTasksToBlock`'s walk traverses it so the block cascade owns everything downstream. Under `'edges'`, current behavior is preserved (a flow's failure handling IS its outgoing edges). Decide `Cancelled` explicitly and once: recommend it never decides ordinary edges under either semantics (a cancelled step's guards were never meant to route anything); document in the spec. Cleanest shape: `DecideGate` takes the effective terminal-decides set (or the semantics value) as a parameter, so both dialects consume one source of truth and the next dialect cannot re-open this hole. No unit test currently pins this shape — `condition-gate.test.ts` tests `Failed` origins with no semantics context; add it.

**Tests.** Unit: `DecideGate` matrix — {Failed, Cancelled} origin × {block, edges} × {true, false, absent-data} verdicts. Differential fixture: the `A→(cond false)→B→D, E→D` shape under `'block'` — D must block, not run (this is exactly the reconvergence class; C3's simulator fidelity fix is a prerequisite, see Phase C). Fixture under `'edges'` asserting drops still work. IT74 extension (**TX19**): live graph, failing action feeding a false conditional edge with an independent healthy route into the join, assert the join blocks under `'block'`.

### R3-3. Flow-dialect `data`/`context` roots must resolve against the invocation, not the origin's output (D2 lands now)

**Severity: HIGH. Verified: PLAUSIBLE — split vote. One reviewer confirmed the full trace independently; the other classes it as Round 1's carried-forward D2 restated with complete mechanism. Both agree on every technical claim. Resolution: this IS D2, now concrete and verified — it stops being a design note and lands in this round.**

**Defect.** `BuildConditionContext` maps the flow-dialect roots `data` and `context` to `envelope.data`/`envelope.context` — keys of the **origin task's** parsed `OutputPayload` (`packages/TaskGraph/src/condition-gate.ts:131-132`). In the engine being replaced, these are the invocation's runtime parameters: `FlowAgentType.buildConditionContext` sets `data: params.data`, `context: params.context` from `ExecuteAgentParams` (`flow-agent-type.ts:503-504`), with `data.userApproval === true` the class's own documented pattern (`:426-429`). Flow agents now always execute compiled (`DetermineInitialStep`, `:1216-1248`; the walker is retained unrouted), but `executeTasksStep`'s Submit carries no `data`, no `context`, no invocation payload (`base-agent.ts:11958-11970`), and `TaskGraphSubmitRequest` has no field for them. So `envelope.data` is essentially always absent → `NO_OUTPUT` → every `data.x`/`context.x` comparison reads `undefined` → clean `false` → the edge silently drops or the exclusive branch loses. No throw, no hold, no diagnostics; the wrong branch runs on **every** invocation, and the validator (`CONDITION_ROOTS` includes both roots, `condition-roots.ts:20-25`) blesses the condition at the door, guaranteeing the silent wrong branch rather than a refusal. This falsifies the module's own parity contract (`condition-gate.ts:100-102`) for two of the five flow roots. Adjacent, same seam: the synthetic `stepResult` shape `{Success, step: originName, result}` matches the spec's documented dialect but not what the walker actually exposed.

**Fix specification.** Thread the invocation envelope end-to-end:

- Extend `TaskGraphSubmitRequest` with the invocation's `data`/`context` (one envelope field), have `executeTasksStep` pass `params.data`/`params.context`, and have `Submit` persist it on the parent's metadata bag (the `persistParent` writer — respect the two-writer discipline).
- `loadGraphState` surfaces the graph-level envelope; `BuildConditionContext` resolves `data`/`context` from it, never from the origin's output. `payload`/`output`/`stepResult` keep their origin-output semantics.
- Decide the `stepResult` shape against the walker's actual exposure in the same commit, and update the spec to whichever is chosen.
- **If any part is deferred**, the validator must refuse `data.`/`context.` roots at submit time in the interim — a loud refusal beats a silent wrong branch on the documented dialect.

Exposure note: shipped demo flows use `payload.*` only; the defect fires on the documented `data`/`context` feature, which is exactly what editor-drawn and LLM-authored flows will use.

**Tests.** IT74 extension (**TX20**): submit a flow-compiled graph invoked with `params.data = { userApproval: true }` branching on `data.userApproval === true`; assert the approval branch runs. Differential fixture: the same flow through walker semantics vs compiled dispatch — the branch taken must match. Unit: `BuildConditionContext` root-resolution matrix (five roots × envelope present/absent).

## Phase B — Correctness fixes, bounded blast radius

### R3-4. `Stop()` during `Start()`'s awaits must not resurrect the dispatcher

**Verified: CONFIRMED (two votes).** `Start()` registers with `ShutdownRegistry` (`TaskGraphDispatcher.ts:490`), awaits `Reconcile()` (`:493`) and the counted startup sweep (`:502-507`) — R2-13's own fix guarantees `Stop()` waits the sweep out — then installs `pollTimer`/`reconcileTimer` **unconditionally** (`:509-513`). A `Stop()` landing during the boot awaits drains, logs "Stopped.", and returns with both timer fields null; `Start()`'s continuation then installs both timers on the stopped instance. `pollOnce` is inert (`:619` guard) but `Reconcile()` has **no running check** (`:585-592`) — `reconcileOnce` mints a provider and executes `ReleaseExpiredClaims` (a real UPDATE returning tasks to Pending) every 120s forever, against a pool the host may have torn down; `ShutdownRegistry.ShutdownAll` clears its items after one pass so nothing ever calls `Stop()` again, and the un-`unref()`'d intervals pin the event loop so the process cannot exit by drain.

**Fix**: re-check `this.running` after the awaits, before `:509` — abort timer installation if stopped; add the `pollOnce`-style guard to `Reconcile()`; `unref()` both intervals (belt and suspenders — Stop() remains the real teardown). Unit test: `Stop()` racing `Start()`'s sweep await; assert no timers exist afterward and `Reconcile()` no-ops.

### R3-5. Human-task request raising must be race-safe, and settle must withdraw the losers

**Verified: CONFIRMED (two votes).** The notify path is unguarded read-then-write in a system whose every other cross-instance write uses CAS: `notifyHumanTaskReady` gates on a snapshot marker (`TaskGraphDispatcher.ts:1542`), `raiseHumanRequest` is SELECT-then-INSERT via plain `Save()` (`:1894`, `:1935` — the exact R2-7 `ensureTaskType` shape), `markHumanTaskNotified` is an unconditional full-row `Save()` (`:1869-1874`), and the migration's `OriginatingTaskID` index is non-unique. Two overlapping instances both insert a `Requested` row and both ping the assignee. When one is answered, `settleAnsweredHumanTasks` settles from the single latest terminal request (`:2016-2042`) and **nothing ever touches the duplicate**: `withdrawOpenRequests` fires only on skip paths (`:853`, `:1251`) and `Cancel`, and both sweeps scope to `Status='Pending'` tasks (`:2007`, `:2138`) which the settled task no longer matches. The duplicate is a durable, un-answerable, immortal inbox item — the exact zombie class R2-10 eliminated on the skip paths.

**Fix**, belt and suspenders: (a) make the raise race-safe — guarded insert or insert-then-reselect keyed on `OriginatingTaskID` + open status (the R2-7 pattern; a filtered unique index on `(OriginatingTaskID) WHERE Status='Requested'` is the durable backstop if a migration is acceptable this round — mind Publish-No-Break, additive, de-dup first); (b) on a normal settle, withdraw **all other** open requests for the task (extend `settleAnsweredHumanTasks` to reuse `withdrawOpenRequests` excluding the answered row) — this also retroactively cleans any duplicates already minted; (c) route `markHumanTaskNotified` through a guarded metadata write. IT74 extension (**TX21**): raise concurrently from two claim stores, assert exactly one open request survives; answer it; assert zero open requests remain after settle.

### R3-6. R2-3 completed: the data-absence classifier must cover the operator shapes the validator blesses

**Verified: CONFIRMED (two votes, both executed the evaluator's exact compiled wrapper).** `DATA_ABSENCE_SIGNATURES` (`condition-gate.ts:79-83`) matches only property-read TypeErrors. Absence surfacing through other blessed operators produces V8 messages the list misses: `"'approved' in payload.details"` with `details` absent → `Cannot use 'in' operator…` → no match → **hold**; `Object.keys(payload.x).length > 0` → `Cannot convert undefined or null to object` → no match → hold. Both shapes are legitimized at the door (`'in'` ∈ `LANGUAGE_NAMES`, `'Object'` ∈ `RESOLVABLE_GLOBALS`, `condition-roots.ts:28-31, 50-53`), and a hold on a terminal origin whose output is frozen is the permanent silent stall R2-3 exists to end; in the exclusive dialect the same `IsDataAbsence` call (`TaskGraphDispatcher.ts:2434`) holds the entire group. The legacy walker rejected a throwing condition and continued (`graph-traversal-engine.ts:190-197`) — these are graphs the walker completed.

**Fix**: add the two V8 signatures (plus their WebKit/SpiderMonkey counterparts) — and harden structurally so the next operator cannot re-open the hole: since the null-safe envelope guarantees roots resolve, classify any `TypeError` from a blessed-surface expression as data absence, keeping `ReferenceError` (unknown root = broken guard) as hold. Unit: extend the R2-3 classification matrix to every member of `LANGUAGE_NAMES` and `RESOLVABLE_GLOBALS` that can throw on an absent chain, asserting `false`-not-hold for each. Differential fixture: the `in`-operator join the walker completed.

### R3-7. R2-5 completed: the determinism tiebreak must be ordinal, not locale-collated

**Verified: CONFIRMED (two votes, sign-flip reproduced in this repo's Node under `en` vs `da`).** `CompareEdgePrecedence`'s final key is no-arg `a.id.localeCompare(b.id)` (`graph-algorithms.ts:544`), which collates under the host ICU locale — `'aa070000'` vs `'ab070000'` flips sign between `en` and `da` (Danish collates the `aa` digraph as `å`), and dependency IDs are UUIDs where `aa` sequences are routine. Two instances with different `LANG` can resolve a genuine `(priority=0, sequence=0)` tie — the persisted default for hand/LLM-authored specs — **differently**, and the same comparator decides the unevaluable-dominance test (`:598-599`), so hold-vs-resolve diverges too. Worst interleaving reproduces R2-5's own dual-skip catastrophe across instances: both XOR branches `Skipped`, graph settles `Complete` having executed neither. The shipped R2-5 test (both input orders, one process) cannot catch this; the function's "Deterministic on persisted state" doc contract (`:522`) is false. Compiled flows are safe (distinct sequences, `flow-graph-compiler.ts:272-279`); Round 2's plan itself prescribed `localeCompare`, so this corrects the prescription.

**Fix**: one-line ordinal codepoint compare (`a.id < b.id ? -1 : a.id > b.id ? 1 : 0`); correct the R2-5 note. Unit test asserting the comparator is Intl-independent (compare the digraph pair, assert the ordinal sign; or run the sort under a forced `Intl` collator and assert it is not consulted).

### R3-8. R2-2 completed: a transient rollup failure must defer delivery, not lose the rollup forever

**Verified: CONFIRMED (two votes; corroborated by three tracks). This is R2-2 scenario 3, verbatim, still open — only the settlement half of that fix's specification shipped.** `rollUpCostToSubmittingRun` returns `Promise<void>` and is awaited with no verdict (`TaskGraphDispatcher.ts:993`); its transient-failure paths — `LoadAgentRunTree` error/empty root (`:1084-1097`), throw (`:1145-1150`), `Save()` false (`:1133-1139`) — all log and return while the pass proceeds to `settleSubmittingRun` and `deliverContinuation`, which claims the marker. A claimed marker permanently excludes the graph from the rescue sweep (`settlement-rescue.ts:107-115`), and the same pass flips the run terminal, so the code's own "retrying on a later settlement" log (`:1092-1096`) promises a retry that structurally cannot come. Durable outcome from **one transient DB error, no interleaving**: a multi-graph run keeps a wrong non-null authoritative `TotalCostRollup` (the `?? TotalCost` fallback cannot save readers from a wrong non-null number); a first-graph run stays permanently null. TX14 covers only the run-read failure path, never a tree-load failure.

**Fix**: give the rollup a verdict — `landed | refused-permanent | failed-transient` — and treat `failed-transient` exactly like `settleSubmittingRun`'s `defer` (`:1000-1006`): skip settle and delivery this pass, `keepRetryingSettlement`, bounded by the existing 24h window. Permanent refusals (`Truncated`, graph-not-in-tree) proceed as today; R2-15's don't-clear-on-transient rule is unchanged. IT74 extension (**TX22**): inject one tree-load failure on the settling pass; assert no marker claim, no terminal run flip; assert the next pass lands the rollup, settles, and delivers exactly once.

### R3-9. `Cancel`'s child writes must be guarded statements, not stale-snapshot full-row saves

**Verified: CONFIRMED (two votes, verified down to `GenerateSaveSQL` and the `@Field_Clear` companion binding).** `Cancel` loads all children (`TaskGraphService.ts:1121-1133`), checks the terminal set against the **in-memory** snapshot (`:556`), and writes `Status='Cancelled'` via `BaseEntity.Save()` (`:557-558`) — an unconditional full-row UPDATE sending every updateable column with a PK-only predicate, per this package's own doctrine (`TaskClaimStore.ts:41-45, 288-296`). A child whose executor's guarded `CompleteClaimed` lands between Cancel's load and that child's save gets its entire outcome overwritten: `Complete`→`Cancelled`, `OutputPayload`→NULL (the null-clear companions make the stale nulls explicit clears), `AgentRunID`/`CompletedAt`/runtime `Configuration` reverted, stale claim columns re-instated on a terminal row. The moment users cancel is exactly when tasks are running; the reverse ordering is safe (CompleteClaimed's predicate refuses), so the hazard is entirely in Cancel's write. Round 1 moved every dispatcher-side transition to guarded single statements for precisely this class; Cancel — reworked this very round by R2-9 — kept the read-then-full-row-save shape.

**Fix**: a claim-store guarded statement per child — `UPDATE ... SET Status='Cancelled' WHERE ID=@id AND Status NOT IN ('Complete','Failed','Cancelled','Skipped')` — with the terminal check **in the statement**, rowcount verdict feeding R2-9's honest-verdict plumbing (rowcount 0 = the child settled meanwhile; leave its outcome intact, report it). IT74 extension (**TX23**): fire `CompleteClaimed` between Cancel's load and save; assert the completed child keeps `Complete` + `OutputPayload` + provenance, and Cancel's verdict reflects it.

### R3-10. `cancelNestedGraphs` must state its task type, and its depth cap must actually engage

**Verified: CONFIRMED (two votes; the inert cap is provable — the sole caller passes literal 0 and recursion restarts at 0).** Two defects in the R2-9 nested-cancel fix. (1) The sub-graph lookup filters only `ParentID IS NULL AND AgentRunID IN (...)` (`TaskGraphService.ts:643`) — no `TypeID` predicate, contradicting its own comment (`:639`) and the engine's doctrine that every graph-mutating operation on the general-purpose `MJ: Tasks` table states its type (`TaskGraphDispatcher.ts:1630-1643`; both type-scoped payload guards in `TaskClaimStore.ts:423, 458`; every `findActiveGraphIDs` arm). Any non-workflow root hierarchy carrying a cancelled run's ID — the D20 user-writable-table threat class the claim store explicitly defends against — gets `Cancelled` written over its children and its requests withdrawn. `loadChildren` (`:1129`) is likewise unscoped. (2) The depth cap is dead code: `Cancel` calls `cancelNestedGraphs(children, context, 0)` with a literal 0 (`:597`), recursion re-enters through `this.Cancel` (`:657`) which restarts at 0, so the `:633` check can never fire — the plan's "bounded by the reinvoke depth cap" promise is false, and a hand-edited `AgentRunID` cycle recurses to stack overflow mid-cancel.

**Fix**: add the workflow-`TypeID` predicate to both the root lookup and `loadChildren`; make depth live by routing recursion through an internal depth-carrying overload (`cancelWithDepth(taskID, context, depth+1)`) and add a visited-set of root task IDs as cycle armor (cheap, and covers linkage shapes the cap's arithmetic does not). IT74 extension (**TX24**): a non-workflow root task stamped with the cancelled run's `AgentRunID` — assert it is untouched; a fabricated cyclic linkage — assert cancel terminates with a verdict, not a crash.

### R3-11. A dispatcher-disabled host must not silently accept graph submissions

**Verified: CONFIRMED (two votes; the watchdog escape hatch was checked and fails — Paused runs are invisible to every sweep).** `MJ_DISABLE_TASK_GRAPH_DISPATCHER=1` suppresses only `StartTaskGraphDispatcher` (`packages/MJServer/src/index.ts:1426-1432`, one boot-time log). But `DurableTaskGraphSubmitter` registers via the generated ServerBootstrap manifest unconditionally (`mj-class-registrations.ts:1162`) — note the flag's authors got the *other* seam right: `DurableEntityActionTaskSubmitter` is registered only inside `StartTaskGraphDispatcher` (`:75`) with a comment saying exactly why ("a submitter without a dispatcher writes Task rows nobody picks up"). The agent path checks only that a submitter is registered (`base-agent.ts:11943-11958`), submits, tells the user "I'll follow up when it finishes" (`:12005-12006`), and parks the run `Paused` (`:13482`). With the flag set on the only server sharing the DB — the flag's own documented use case, running IT74 against a live MJAPI that keeps serving clients — the graph sits `Pending` and the run sits `Paused` forever with zero per-submission diagnostics, recoverable only by noticing, unsetting, and restarting, after which the stale graph executes hours later.

**Fix**: extend the flag's existing (correct) treatment of the entity-action seam to the agent seam: when disabled, the host neutralizes the manifest-registered submitter at boot — either unregister `TASK_GRAPH_SUBMITTER_KEY` or set a host-level kill switch the submitter's `Submit` consults and **throws loudly on**. The agent then takes its existing no-submitter path and reports honestly instead of promising a follow-up that will never come. Pair with the carried-forward IT74-diagnostics item (below) so the refusal message and the test suite's contamination message name the same flag. IT74 extension (**TX25**): with the kill switch set, an agent graph submission must fail loudly at submit time — no `Pending` graph row, no `Paused` park.
