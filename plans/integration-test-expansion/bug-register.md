# Bug Register — defects surfaced by the integration-audit

Companion to **[README.md](README.md)** / **[test-catalog.md](test-catalog.md)**. Every defect/anomaly the 9-cluster adversarial audit surfaced, made **fix-ready**. Each has a **disposition** so we can decide what lands in this omnibus quality PR (#3181) vs. what's a test-only pin vs. what needs your sign-off.

**Dispositions:**
- **FIX-NOW** — clear, low-risk fix that fits the quality PR; pair with a guarding test.
- **DECIDE** — real defect but the fix is a security/architecture/behavior call → **AI proposes, human approves** (per the §3a governance rule). Don't land silently.
- **PIN** — current behavior is by-design (or an accepted trade-off); write a test that *pins* it, change no code.
- **VERIFY** — suspected but unconfirmed; the first task is a test that proves whether it's real.
- **GUARD** — not a bug today, a latent risk; add a test that fails if it *becomes* one. No code change.
- **DONE** — already fixed in-repo; add a regression test so it can't return.

> **Note on scope:** writing the tests is the green-lit work; *fixing* these is a related decision. Nothing here is fixed yet. The security-sensitive ones (B1, B7, B8) especially must not be touched without your explicit go-ahead.

| B26 | **CodeGen writes DDL for unchanged entities but never EXECUTES it — self-perpetuating.** Root cause of B24, and structurally the more serious finding. The index generator is correct: `generateForeignKeyIndexes()` emits a statement for every field with a `RelatedEntity`, with no skip-gate, and the checked-in `SQL Scripts/generated/__mj/*.index.generated.sql` files **already contain all six** of B24's statements. | B27 | **`autoIndexForeignKeys()` defaults to `false` when absent**, and it is commented out in `distribution.config.cjs:80,86`. | B28 | **SQL Server FK-index generation can emit `CREATE INDEX` on a non-existent column.** The PostgreSQL generator filters `!field.IsPrimaryKey && !field.IsVirtual`; the SQL Server generator does not. Not currently observed failing (no such FK field exists today), which is exactly why it's worth fixing before one appears. | `SQLServerCodeGenProvider.ts:496-514` vs. the PG generator | Med (latent) | Add the same `!IsPrimaryKey && !IsVirtual` field filter the PG path already has. Small and symmetrical. | **FIX-NOW** (next CodeGen PR) | MC4 would catch the resulting failure only after it broke a run |

**B26 status — deliberately NOT fixed in PR #3196.** Investigated to a confident stop. `logSQLForNewOrModifiedEntity` does expose a `forceLog` bypass, but `shouldLog` fans out to **two fused destinations**, so forcing it has out-of-scope side effects: (1) `SQLLogging.appendToSQLLogFile` would append every entity's FK-index DDL to **every** `CodeGen_Run_*.sql` migration on **every** run; and (2) `TempBatchFile` would become permanently non-empty, so the `else` branch at `sql_codegen.ts:308-311` — which executes the combined files when nothing changed — could never fire again, altering **view/proc execution**. `forceRegeneration.indexes` carries the same bloat plus unrelated regeneration. The correct fix is to **separate execute-from-log**: run idempotent index DDL every time without writing it to the migration unless the entity changed. Contained and additive, but it introduces a new per-run DDL sweep that needs live-DB validation — so it belongs in its own DB-validated PR, not bolted onto a default flip.

> **PG parity (important for whoever picks up B26):** PostgreSQL never executes index DDL during codegen *at all* — `executeEntityInPhases` rebuilds TVF/view/CRUD/perms with **no index phase**, and `TempBatchFile.cleanup()` runs unexecuted (`sql_codegen.ts:292-299`). On PG the DDL only ever reaches the migration file, gated identically. **So PG shares the gap through the logging channel.** A B26 fix that only addresses *execution* would fix SQL Server and silently leave PostgreSQL broken. (Traced statically; the PG pipeline was not run.)
