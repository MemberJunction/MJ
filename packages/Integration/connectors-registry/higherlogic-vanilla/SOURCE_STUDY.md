## 0. Executive summary

Higher Logic Vanilla publishes its API v2 contract as a **live OpenAPI v3 spec served by every
Vanilla-hosted community at `{community}/api/v2/openapi/v3`**. Two independent public communities
were used to recover the fullest possible union of that contract, credential-free:

| Community | Reachability | paths | schemas | Notable addons enabled |
|---|---|---|---|---|
| `open.vanillaforums.com` | **Live, unauthenticated, direct fetch** (HTTP 200) | 237 | 290 | core forum/discussion feature set; no Knowledge Base |
| `success.vanillaforums.com` | Live raw endpoint now requires `Garden.Settings.Manage` (403 anon); **full spec is embedded verbatim in the public KB article HTML** (`kb/articles/1842`) | 316 | 350 | Knowledge Base/Articles, Analytics dashboards, AI settings |
| **Union (merged)** | — | **335** | **380** | everything both instances expose |

Walking the merged spec's `paths` in code (never by hand) yields **79 independently-addressable REST
resources ("doors")**, of which **51 are COVERABLE record types** with real numeric `<object>ID` (or
documented string business-key) primary keys, real scalar foreign keys, real `page`+`limit`+Link-header
pagination, and — for the large majority — real Create/Update/Delete paths and HTTP methods. The
remaining 27 doors (+1 container-fold) are **INFORMATIONAL**: settings singletons, pure action/utility
endpoints, or virtual cross-object unions.

**Gate decision: PROCEED.** Real-OpenAPI-coverage is far above the 0.7 threshold — every hard-constraint
field the connector needs (APIPath, PK, FK, pagination shape, watermark field, per-operation CRUD
columns) is directly provable from the merged spec, not deferred or guessed.

## 2. Deep study of the OpenAPI spec (the primary source)

### 2.1 File layout / structural conventions

- Standard OpenAPI 3.0.x document: top-level `openapi`, `info`, `servers`, `paths`,
  `components.schemas`, `components.parameters`.
- **Every path is grouped under a single top-level segment** ("door"), e.g. `/discussions`,
  `/discussions/{id}`, `/discussions/{id}/comments` are all under the `discussions` door. This
  door-grouping is walked programmatically (never eyeballed) to build the object catalog — see §4.
- **Vendor-native `tags`** on almost every operation (78 distinct tag values found) mirror the
  Vanilla Dashboard's own sidebar groupings almost 1:1 with the doors (e.g. tag `"Reports &
  Escalations"` spans the `appeals`, `escalations`, `reports`, `report-reasons` doors as one
  Dashboard-visible section). These vendor-native tags are the evidentiary basis for the taxonomy
  groupings in §5 — the categories **emerge from the source's own tagging**, not from an invented
  scheme.
- **List/single schema-name split.** A recurring vendor convention: the LIST endpoint
  (`GET /articles`) often returns a lighter/legacy-named schema (`ArticleSimple`) while the
  single-GET (`GET /articles/{id}`) returns the fuller, canonical name (`Article`). Also observed on
  `tags`→`Tag`/`LegacyTag`, `themes`→`Theme`/`Themes`, `locales`→`Locale`/`LocaleConfig`,
  `resources`→`Resource`/`ResourceFragment`. The extractor script (§4) resolves this by unioning both
  schemas' fields and preferring the single-GET's name as canonical — see the idiosyncrasy note in §7.
- **Request/response DTO multiplicity.** Every writable resource has `<Name>Post` / `<Name>Patch` (and
  occasionally `<Name>Put`) request-body schemas distinct from the canonical read schema. These are
  NOT separate record types — see the reconciliation ledger in §4.2.
- **Nested/nested-list nesting.** Some coverable objects are reached only via a parent's own path
  (e.g. `/user-mentions/users/{userID}`, `/moderation-messages`), and several doors return true
  parent→child relationships expressed as scalar FK fields rather than nested arrays (Vanilla's API
  is flat/relational in its response shapes — a Discussion carries `categoryID`, not an embedded
  category object; expansion is opt-in via the `expand` query param on many list endpoints).
- **`allOf` composition** is used for a handful of schemas (e.g. `LocaleConfig = allOf(Locale,
  TranslationServiceType)`) — the extractor's schema resolver flattens `allOf`/`oneOf`/`$ref` chains
  recursively rather than reading only the first level.
- **A few operations omit the `type: array` marker** on an otherwise-array response schema (observed
  on `GET /events` — it declares `{"items": {"$ref": "FullEvent"}}` with no `type` key at all). This
  is a genuine vendor spec-authoring gap; the enumerator treats presence of `.items` alone as
  sufficient array evidence (documented fix in the script, not a workaround hidden from view).

### 2.2 Patterns and motifs

- **Primary keys**: overwhelmingly `<door-singular>ID` (numeric), e.g. `discussionID`, `commentID`,
  `userID`. A minority use a UUID-suffixed key (`exportUUID`, `iconUUID`, `automationRuleDispatchUUID`)
  or a documented string business-key (`ProfileField.apiName`, `ReactionType.urlCode`,
  `Widget.name`) — never inferred, always the field the OpenAPI path parameter on the
  GetById/Patch/Delete path itself names.
- **Foreign keys**: scalar `<base>ID`/`<base>UUID` properties. The vendor is extremely consistent
  about `insertUserID`/`updateUserID`/`lastUserID`/`dismissUserID`-shaped actor references, all
  correctly resolved to `User` by the extractor's actor-pattern rule.
- **Watermarks**: `dateUpdated` (preferred) or `dateInserted` (fallback for insert-only/no-update
  resources) is present on the large majority of coverable objects (see the `watermark` column in
  §5's tables) — a strong, source-provable `IncrementalWatermarkField` candidate per object.
- **Pagination**: universally `page` + `limit` query params on list endpoints (confirmed by the
  `listParams` column containing `page,limit` on nearly every coverable object), Link-header
  navigation (`rel=first/last/prev/next`), a `Paging-Next` response header guaranteeing "more data
  exists" even when a page returns fewer rows than `limit` (permission-filtered rows can shrink a
  page without ending the result set) — documented explicitly in KB article 40 (§3).
- **Sparse fieldsets**: a `fields` query param is present on essentially every GET operation
  (`fields` appears in nearly all 51 coverable objects' `listParams`) — a genuine, vendor-supported
  field-projection mechanism, confirmed by KB article 40.

### 2.3 Scope — what's covered, what's explicitly NOT

Covered: the full REST surface of both Vanilla-hosted communities probed (content/discussion
platform, knowledge base, groups/products/subcommunities, moderation/trust-and-safety, site admin,
webhooks/automation/integrations config).

NOT covered by the OpenAPI spec itself (informational-only per §6, or entirely absent):
- **SSO/OAuth2/SAML/OIDC/jsConnect configuration** — these are Dashboard-configured authentication
  FLOWS, not REST resources with their own CRUD surface in API v2. (The operator context doc's Tier 5
  "official SSO documentation" pointer is correct in spirit but no such distinct KB article was
  fetched in this pass — flagged as a gap in §8 since SSO is out of scope for a sync-style connector
  in any case.)
- **A distinct "reaction event" (who reacted to what, when) resource** — the `/reactions` door
  returns the CATALOG of possible reaction TYPES (Like, Promote, Disagree, etc.), not a log of
  individual reaction events. Individual reactions are only reachable nested under a
  discussion/comment's own record (`reactions` property on `Discussion`/`Comment`/`Article`), not as
  an independent top-level list endpoint. This is a real, source-confirmed absence, not an
  extraction miss — noted in §7.

## 3. KB prose sources — study

### `kb/articles/40-api-v2-overview` (pagination & field selection)
Confirms two pagination styles (numbered: full first/last/prev/next; "more": first/prev/next only,
used where a total-row COUNT would be too expensive to compute) — both delivered via the RFC-5988
`Link` response header, never a body-embedded cursor. Confirms the `fields` sparse-fieldset param
works on every GET and on CSV export. Extracted text: `sources/kb-40-api-v2-overview.extracted.txt`.

### `kb/articles/44-rate-limits`
Explicit numeric limits: **GET: 300 req/min/IP; POST/PUT/PATCH/DELETE: 120 req/min/IP**; HTTP 429 on
violation (auto-lifts after 1 minute); a **hard ceiling of 250 requests within 10 seconds** can trigger
a longer block requiring Vanilla Support to manually lift. Extracted text:
`sources/kb-44-rate-limits.extracted.txt`.

### `kb/articles/41-authenticating-apiv2-calls-with-personal-access-tokens`
Confirms Bearer-token (`Authorization: Bearer <token>`, preferred) and `access_token` query-string
(fallback) auth. Personal access tokens are user-scoped (not a separate service-account concept) and
gated by the `Garden > Tokens > Add` permission. Extracted text:
`sources/kb-41-personal-access-tokens.extracted.txt`.

## 4. Mechanical Universe Anchor — full accounting ledger

Per the enumeration discipline, the object universe is **computed by scripts run over the saved raw
source**, never hand-typed. Three independent, code-computed signals were produced and reconciled:

### 4.1 Door-level walk (the primary, REST-appropriate anchor)

`node scripts/enumerate-vanilla-catalog.mjs sources/vanilla-openapi.merged.v3.json`

```
totalDoors: 79   (walking spec.paths, grouped by top-level segment)
containerFolds: 1   ({"primaryRef":"ProductMessage","foldedDoors":["product-message","product-messages"]})
coverableCount: 51
informationalCount: 27
```//
Accounting: `79 doors == 51 coverable + 27 informational + 1 (the 2 folded doors collapse to 1 unit)`.
**Closes exactly.**

### 4.2 Raw component-schema-level ledger (the finer, OpenAPI-DTO-level cross-check)

`enumerate-catalog.mjs` (the shared generic enumerator) reports **342** record-shaped schemas out of
**380** total `components.schemas` entries (38 are pure enum/scalar leaf types, excluded by that
script's own definition of "record type"). This 342/380 is a coarser, schema-NAME-level signal that
does not by itself distinguish an independent resource from a request/response DTO variant of one —
OpenAPI/REST specs are expected to have far more schema names than independent resources, because
every writable resource contributes `<Name>Post`/`<Name>Patch` DTO schemas alongside its canonical
read schema. `scripts/reconcile-schema-ledger.mjs` buckets **every one of the 380 raw schema names**
by TOP-LEVEL PATH REACHABILITY (is this schema ever the direct — or array-item — schema of some
path's request body or 2xx response, anywhere in the merged spec?) rather than by suffix-guessing:

| Bucket | Count | Meaning |
|---|---|---|
| `coverable` | 46 | Schema name is the literal canonical name of one of the 51 coverable units (the remaining 5 coverable units' canonical names — e.g. door-derived names with no exact 1:1 schema key — are covered by the `topLevelOtherEndpoint` bucket instead) |
| `informational` | 10 | Schema name is the literal canonical name of one of the 27 informational units |
| `topLevelOtherEndpoint` | 142 | Directly returned/consumed by SOME path operation (a real REST-contract-connected type) but is a request/response DTO variant (`Post`/`Patch`/`Aliases`/etc.) of an already-covered or already-informational door, or a folded-door variant |
| `nestedValueObject` | 182 | NEVER directly returned by any endpoint — a property-level value type referenced only from inside another schema's `properties` (e.g. `SrcSet`, `CategoryPreferences`, analytics computation-result shapes, enums) |
| **`unaccounted`** | **0** | — |

`46 + 10 + 142 + 182 + 0 == 380`. **Closes exactly, zero unaccounted.** Full bucket contents (every
name, not just samples) are in `sources/derived/schema-ledger.full.json`.

### 4.3 Why the door-level count (79/51/27), not the raw schema count (380/342), is `TaxonomyLeaves`

A REST/OpenAPI-described API's natural "coverable object" unit is the independently-addressable
**resource** (the door), not every named request/response DTO schema. `TaxonomyLeaves` uses the
door-level, script-computed, PascalCase-normalized names (§4.4) — this is the level at which the
connector's IOs, PKs, FKs, and per-operation CRUD columns actually live per
`connector-code-conventions.md`.

### 4.4 Name normalization (still script-computed, not hand-typed)

`scripts/normalize-taxonomy-names.mjs` applies a small, explicit, logged override table (14 entries,
each with a one-line reason — e.g. `CategorySchema→Category` strips the vendor's `…Schema` suffix
convention; `UserFragment→OnlineUser` avoids colliding with the real `User` leaf since that door is
reached only via `GET /online`) to the 51 raw canonical names, asserts the result is collision-free
(bijective), and emits the final 51-name `TaxonomyLeaves` array. Full mapping (raw name → normalized
name → reason) is in `sources/derived/taxonomy-leaves.mapping.json`.

### 4.5 Excluded scaffolding

**None found.** Both source communities' OpenAPI output is 100% vendor-product surface — no
test-fixture, sandbox-stub, or internal-tooling leakage was observed in either spec (no
`Bucket_Test`-style names, no `_deprecated`/`_internal` folder markers). One (1) genuinely deprecated
door was found and correctly folded into INFORMATIONAL rather than excluded outright: the
`statuses`-adjacent tag literally named **"Statuses (Deprecated)"** in the merged spec — its schema
(`Status`) is still coverable (real CRUD, real door) so it stays in `TaxonomyLeaves`; the vendor's own
"(Deprecated)" tag is noted here for extraction-time awareness, not treated as exclusion grounds since
the endpoints are still live and documented.

## 7. Idiosyncrasies to inform extraction

1. **List/single schema-name mismatch** (Article/ArticleSimple, Tag/LegacyTag, Theme/Themes,
   Locale/LocaleConfig, Resource/ResourceFragment) — the extractor unions both schemas' fields and
   canonicalizes on the single-GET's name. Any future extraction pass reading this spec directly
   (rather than via the saved enumerator output) must replicate this or it will under-name/under-field
   these 5 objects.
2. **`GET /events` omits `type: array`** despite returning a list — a genuine vendor OpenAPI-authoring
   gap, not a signal that `/events` is non-list. The enumerator treats `.items` presence alone as
   array evidence.
3. **`mediaUUID` is a self-referential alternate identifier, not a real FK**, despite matching the
   `<base>UUID`→FK naming heuristic (MediaItem's own PK is `mediaID`; `mediaUUID` is a second,
   UUID-shaped identifier for the SAME record, not a pointer to a different "Media" object). Flagged
   here so the ioiof-extractor's multi-signal FK aggregation doesn't emit a spurious self-referencing
   FK without cross-checking against the sibling-object-exists rule (extractor-conventions: "field name
   == sibling IO's emitted PK" — no `MediaItem`-named sibling with PK `mediaUUID` exists, which should
   suppress this candidate FK).
4. **`ReactionType` is a type catalog, not an event log** (§2.3, §5.5) — do not conflate with "who
   reacted to what."
5. **`ProductMessage` is reached by two path prefixes** (`/product-message` singular tag alias and
   `/product-messages` plural) resolving to the identical schema — correctly container-folded to one
   unit; not two objects.
6. **A regex-greediness trap in naive FK-name derivation**: any field ending in `...UUID` (e.g.
   `mediaUUID`, `iconUUID`, `exportUUID`) will be mis-split by a naive `/^([a-zA-Z]+)(ID|UUID)$/`
   regex due to backtracking always finding the shorter `ID` suffix first (`mediaUUID` → `mediaUU` +
   `ID` → wrong base `"MediaUu"`). The enumerator resolves the `UUID`/`ID` suffix by explicit string
   test (longest-first), not by trusting regex-alternation order (which does NOT fix it — verified;
   see the code comment in `scripts/enumerate-vanilla-catalog.mjs`). Any hand-written FK-derivation
   code elsewhere should use the same explicit-suffix-test pattern.
7. **Deprecated-but-live**: the `Status` object's vendor tag reads `"Statuses (Deprecated)"`, yet the
   endpoints are fully live with real CRUD. Kept as coverable (§4.5); flagged so extraction doesn't
   silently skip it, but the connector should treat it as lower-priority/soft-deprecated in
   documentation.
