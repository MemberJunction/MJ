# Atomic metadata sync push and database provider post-commit queuing

## TL;DR
Transactional atomic sync pushing and post-commit queue serialization land on the certified LTS line lts/6.1. This patch restores all-or-nothing push atomicity, introduces transaction post-commit queuing to defer action hooks, and resolves installer, sub-agent execution, and cross-server caching defects.

## Bug Fixes
- **Atomic and transactional metadata push operations** (`@memberjunction/metadata-sync`, `@memberjunction/core`, `@memberjunction/postgresql-dataprovider`): Previously, `mj sync push` committed each directory graph independently and in parallel, leaving metadata half-applied on failure and potentially deadlocking against itself when view reads hit other rows during the insert read-back. Push operations are now atomic and all-or-nothing by default, running within a single transaction one JSON-root graph at a time. Any record error (including non-throwing `status: 'error'` and Phase 2.5 deferred failures) rolls back the entire push and restores metadata files. Parallel, non-atomic commits remain opt-in per-entity with `push.isolatedTransactions: true` in `.mj-sync.json`, and are overridable via CLI flags (`--isolated-transactions` / `--no-isolated-transactions`). The interactive commit confirmation prompt has been removed, and write-deferred files with deletions are written post-failure only if their records actually committed to prevent key loss.
- **Provider-level transaction post-commit queue serialization** (`@memberjunction/core`, `@memberjunction/generic-database-provider`, `@memberjunction/sqlserver-dataprovider`, `@memberjunction/actions-base`, `@memberjunction/actions`): Fire-and-forget tasks dispatched during a save could register or execute after a transaction had already aborted or settled, causing state drift and firing after-hooks on rolled-back rows. This release introduces a provider post-commit queue via `DatabaseProviderBase.RunAfterCommit(task, description, token?)` and `CapturePostCommitToken()`. Registered tasks wait for the outermost transaction to commit and are discarded on rollbacks, failed commits, or abandoned transaction states. Entity and AI action dispatchers capture a `PostCommitToken` before their first `await` and pass it down, binding tasks to the transaction that caused them rather than whichever transaction is open during registration. This prevents busy-spinning during long transactions, and ensures tasks whose transactions have committed wait for unrelated transactions to end before executing.
- **LTS database dispatcher least-privilege SQL permissions and guarded writes** (`@memberjunction/task-graph`): The durable task-graph dispatcher works under a least-privilege login again (#4575). `TaskClaimStore`'s guarded writes have been moved from raw SQL against the `Task` and `AIAgentRun` base tables into dedicated stored procedures granted to the `cdp_Developer` and `cdp_Integration` database roles, and its two reads have been relocated to the `MJ: Tasks` entity. Rowcount arbitration, guards, and the single-clock rule remain unchanged. A refused write now reports as a failure (rather than a lost race) to halt the wave, and the dispatcher probes for `EXECUTE` grants on startup.
- **Multi-server engine state cache-event synchronization and derived-state rebuilds** (`@memberjunction/core`, `@memberjunction/ai-engine-base`): In multi-server Redis pub/sub deployments, applying external cache payloads replaced configuration properties but bypassed `AdditionalLoading`, leaving derived collections (such as grouped child collections or memoized lookups) referencing discarded instances. This caused model selection to fail with "No suitable model found" in `AIEngineBase` while count-based health checks passed. `AdditionalLoading` is now invoked on both the payload fast path and full-reload fallback. Property-change notifications are emitted only after the rebuild (ensuring subscribers cannot observe pre-rebuild state), and are now correctly emitted on the payload path. To prevent unbounded memory growth, `AIEngineBase.AdditionalLoading` has been refactored to be linear and idempotent, bucketing child rows in a single pass and replacing parent collections outright (reducing complexity from O(parents × children) to O(parents + children)).
- **Installer robustness and interactive prompt fixes on fresh hosts** (`@memberjunction/installer`): Resolves four defects blocking `mj install` on fresh environments. Turbo build summary parsing has been corrected: previously, a regex expected a literal `Failed:` before each failure name, reading only the first failure and ignoring subsequent ones, and matched nothing when names were wrapped in ANSI escapes under `FORCE_COLOR` (triggering false `BUILD_FAILED` states). Both installer phases now share a classifier that strips ANSI escapes and parses the entire list, and installer-spawned turbo and codegen builds pin `FORCE_COLOR=0`. To prevent ENOENT failures during package manager probes, the target directory is now created before preflight probes are run. Interactive prompts (`DatabaseHost`, `DatabasePort`, `DatabaseTrustCert`, `APIPort`, and `ExplorerPort`) are no longer pre-answered, avoiding a default `false` for `DatabaseTrustCert` that failed migrations on self-signed SQL Servers. Finally, database connectivity checks no longer report verified status on simple TCP probes, and false positives for missing `sa` setups have been resolved.
- **CodeGen daemon command checking and post-install reporting** (`@memberjunction/codegen-lib`): Persistent `npm start` boot checks with a 30-second timeout previously caused CodeGen to report working installations as failed. Since servers cannot exit on their own, the timeout was hardcoded as a failure, terminating the pipeline even when the API had booted perfectly. `CommandInfo` now carries an `isDaemon` flag, declaring that staying up for the entire timeout constitutes success, while exiting before the timeout remains a failure. This flag has been applied to the MJAPI boot check in both distribution and default configurations.
- **Metadata pull record preservation for unregistered entity classes** (`@memberjunction/metadata-sync`): `mj sync pull` previously read primary keys through typed properties (`record.ID`). When an entity's subclass was unregistered in the CLI process (e.g., from an unloaded Open App package), records returned as bare `BaseEntity` instances and keys resolved to `undefined`. This caused all pulled records to overwrite each other under the same key, committing only a single record with an empty `primaryKey` that caused duplicate key errors on subsequent pulls (#3415). Keys are now dynamically read via `BaseEntity.Get()`, and `FileWriteBatch` rejects updates with missing key fields while allowing valid empty-looking values (like empty strings or `"null"`). Key-matching string construction has been unified, and internal separator characters (`|`) within key values are escaped to prevent collisions.
- **In-process sub-agent execution modes for Flow agents** (`@memberjunction/ai-agents`): Flow agents can now run as sub-agents and return execution payloads when awaited (#4555). Flow agents invoked with a `parentRun` or `agentTypeParams.executionMode: 'inRun'` process steps sequentially in-process and return their payloads, rather than dispatching to the task-graph dispatcher. Top-level runs without these options are still dispatched to the task graph, and each run records its execution mode as a `Decision` step.
